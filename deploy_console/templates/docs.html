NOTBOOK CONSOLE — PLAIN ENGLISH GUIDE

← Back to console

This page explains every part of the Deploy Console in everyday language. You do not need to be a developer to use it.

Two apps, not one
Think of roommates sharing a house:
  • Telegram bot — talks to students, answers questions from your books.
  • This console — your control panel: keys, book uploads, hosting buttons, health checks.
Each roommate has their own keychain (secrets). Putting keys on the bot does not automatically give them to the console, and the reverse is also true. On Render you usually have two Web Services — one for each.

1. What is this console?

A private website for the owner (you) to manage Notbook without living in a terminal all day. Students never open this. Only people who know the console password (if you set one) should.

Typical day-to-day uses:

  • Check whether the live bot is ONLINE.
  • See which keys this console has vs the bot.
  • Upload a PDF textbook so it shows up under Telegram → Menu → Books.
  • Redeploy or read logs on Render when something looks stuck.
  • Link the two services so they can talk to each other safely.

2. The top of the screen

  • NOTBOOK DEPLOY CONSOLE — brand title. The blinking block is just style.
  • Meta line (top right) — quick summary like BOT ONLINE · CONSOLE READY or what still needs fixing.
  • Tabs — STATUS, SECRETS, CONFIG, LIBRARY, LINK, RENDER, LOCAL, DEPLOY, ARTIFACTS, and DOCS (this page).
  • Footer clock — current time in UTC. Handy when comparing with Render logs.

3. STATUS tab — “is everything awake?”

A live health sheet. Hit REFRESH after you change keys or wake a sleeping free-tier bot.

What the big text block means

  • PROJECT — folder path where the code lives on this machine/service.
  • PYTHON — which Python version is running the console.
  • TELEGRAM BOT ONLINE / OFFLINE — live check, not a guess. The console calls your bot’s public address at /health. If that answers, the bot is treated as ONLINE. On a laptop it can also notice a local bot process. Old versions only looked for a local process, so cloud bots always looked “stopped” even when Telegram worked. That’s fixed.
  • URL — the bot address from BOT_BASE_URL. If this is empty, the console can’t ping the cloud bot.
  • CHECK — how we decided: remote_health (public ping), remote_linked (ping + shared secret details), local_pid (process on this PC), or none (no URL and no local process).
  • LOCAL PID — “is the bot process on this same computer?” On Render this is usually no, and that’s normal. Your bot is a different service.
  • CONSOLE READY YES/NO — does this console have Telegram + Gemini + Pinecone keys? You need YES to upload books from the LIBRARY tab. The bot can be happily answering students while the console still says NO — different keychains.
  • SECRETS ON CONSOLE — checklist for keys on this website’s Environment (or local .env).
  • SECRETS ON BOT — what we learn by asking the bot (needs link token + working bot URL).
  • STACK — AI model names, embedding size, Pinecone index name, reranker setting from config.

Buttons

  • REFRESH — re-run all checks now.
  • GENERATE ARTIFACTS — same idea as the ARTIFACTS tab: write helper deploy files to disk.
Bot shows OFFLINE but Telegram still works?
Free hosting often puts the bot to sleep. Open the bot’s public URL once in a browser (the same URL as BOT_BASE_URL), wait ~30 seconds, then hit REFRESH. Also double-check BOT_BASE_URL has no trailing slash and points at the bot service, not the console.

4. SECRETS tab — passwords and API keys

This is the keychain for this console when you run it on your computer (saved into a file called .env). On Render, also paste the same values under the service’s Environment page so they survive restarts and redeploys.

Each field

  • TELEGRAM_BOT_TOKEN — from Telegram’s BotFather. Proves “I am this bot.” Without it, nothing can talk on Telegram.
  • GEMINI_API_KEY — from Google AI. Powers answers and turning book text into searchable pieces.
  • GEMINI_API_KEYS — optional. Several keys separated by commas if you want rotation/backup.
  • PINECONE_API_KEY — from Pinecone. The online “bookshelf database” that stores book chunks.
  • ADMIN_USER_IDS — your Telegram numeric user id(s). Who is allowed to admin-upload books in Telegram. Comma-separated if more than one person.
  • PORT — network port the bot listens on (usually 8080 on hosts like Render; they often set this for you).
  • RENDER_API_KEY — optional. Lets the RENDER tab control deploys/logs from here (create under Render → Account → API Keys).
  • RENDER_SERVICE_ID — which Render service is the “preferred” one when you press deploy buttons. Usually filled from the RENDER tab via SET AS PREFERRED.

Link-related fields (BOT_BASE_URL, CONSOLE_BASE_URL, INTERNAL_SERVICE_TOKEN) live on the LINK tab. Console password is set as Environment vars CONSOLE_PASSWORD / optional CONSOLE_USER (default user name: admin).

Buttons

  • SAVE .ENV — write the form into the local .env file.
  • REVEAL / RELOAD — reload from disk and show values unmasked (careful on shared screens).

5. CONFIG tab — how the AI behaves

These knobs write into config.yaml. Most people leave the defaults. If something already works, don’t random-tweak mid-study-session.

LLM (the “writer”)

  • model_name — which Gemini brain to use for answers.
  • temperature — how creative vs strict. Lower = more boring and consistent (good for study).
  • max_output_tokens — hard cap on how long a single AI reply can be.

EMBEDDINGS (turning text into searchable numbers)

  • provider / model / dimension — how book chunks are encoded for Pinecone. Changing dimension means old vectors no longer match — you’d re-upload books.

RERANKER (second pass on search results)

  • enabled — on/off.
  • backend — which tool re-orders the best chunks (auto is fine).
  • candidate_k / top_k — how many chunks to consider, then how many to keep.

PINECONE / RAG (search settings)

  • index_name — name of the Pinecone index (bookshelf warehouse).
  • dimension — must match embeddings dimension.
  • top_k_dense — how many vector matches to pull first.
  • hybrid_alpha — balance between “meaning search” and “keyword search.”
  • router.max_namespaces — when no book is selected, how many books to probe at once.
  • router.use_probe — smart book picking on/off.

FAITHFULNESS (don’t invent medical claims)

  • enabled — check answers against retrieved book text.
  • min_claim_score — how strict the check is.
  • max_retries — how many times to rewrite if a claim looks unsupported.
  • strict — when true, prefer refusing/softening over shaky claims.

BOT / ADHD (message shape for real humans)

  • rate_limit_per_minute — spam guard per user.
  • max_message_chars — longest Telegram-style chunk before splitting.
  • max_facts — how many bullet facts in a compact answer.
  • max_summary_chars — short summary length cap.

Buttons

  • SAVE CONFIG — write changes to config.yaml.
  • RELOAD — discard form edits and re-read the file.

On Render, config changes on the console service don’t magically rewrite the bot service’s file unless you deploy the same repo change or sync intentionally. Prefer changing config in git and redeploying both if they share the repo.

6. LIBRARY tab — put textbooks into the bot

This is how a PDF becomes something students can pick under Menu → Books in Telegram.

Fields

  • PDF file — the textbook file from your computer.
  • Display name — friendly label students see (example: “Rakel”, “Murtagh”). Behind the scenes the storage “shelf” is named like global|That Name.

Buttons

  • UPLOAD TO PINECONE — start the pipeline: read PDF → split into chunks → embed with Gemini → store in Pinecone. Needs Gemini + Pinecone keys on this console.
  • REFRESH BOOKS — re-list books already indexed (from this console’s view of the library).

Progress area

  • Phase — plain words for the current step (reading, embedding, upserting, done, error…).
  • Percent bar — rough progress so you know it isn’t frozen.
  • Chunk counts — how many pieces processed vs total.
  • job id — internal job number (useful if you open logs or ask for support).
  • LIVE LOGS — play-by-play. Heartbeats mean “still working.”
  • INDEXED BOOKS — list of display names already in the system.
First upload of a new book name
You may see something like “namespace not found” while clearing the old shelf. That’s normal the first time — there was nothing to delete yet. Upload continues.

After a successful upload: open Telegram → your bot → Menu → Books → pick the book → ask questions. Re-uploading the same display name replaces that book’s content.

7. LINK tab — make bot and console friends

When both run on the internet (two Render services), they need each other’s public URL and a shared secret so random strangers can’t call the private control endpoints.

Fields

  • BOT_BASE_URL — public URL of the bot service, e.g. https://notbook-bot.onrender.com (no slash at the end).
  • CONSOLE_BASE_URL — public URL of this console.
  • INTERNAL_SERVICE_TOKEN — a long random password you invent once. Put the same value on both services’ Environment.

Buttons

  • SAVE LINK — store those three values for the console.
  • LINK STATUS — show what the console currently thinks is configured.
  • PING BOT — simple “are you there?”
  • PULL BOT STATUS — ask the bot for a richer health + secrets checklist.
  • PULL BOT BOOKS — ask the bot which books it currently sees.
  • PULL BOT CONFIG — ask the bot for its running config snapshot.
  • PUSH: CLEAR BOT CACHE — tell the bot to drop temporary memory (after big library changes).
  • PUSH: REFRESH LIBRARY — tell the bot to re-read the book list.
  • SYNC SECRETS VIA RENDER API — copy keys from this console into the bot’s Render Environment (needs RENDER_API_KEY). Powerful; double-check you’re targeting the right service.

Output boxes

  • LINK / BOT RESPONSE — raw result of the last ping/pull/push.
  • EVENTS FROM BOT — notes the bot posted back (for example after start/upload), if webhooks are set up.

8. RENDER tab — control your host from here

Render is the cloud host. This tab uses RENDER_API_KEY so you don’t have to click around the Render website for every small job. If the API key is missing, these buttons will complain — set it under SECRETS / Environment first.

SSH public key (optional)

  • SHOW SSH KEY — shows a public key you can paste into Render Account → SSH Public Keys (shell access on plans that support it).
  • COPY PUBLIC KEY — copies that text for you.

Day-to-day deploy work does not need SSH. The API key is enough for deploys, env, and logs.

Service controls

  • LIST SERVICES — load all services on your Render account into the dropdown.
  • Active service dropdown — pick bot or console service carefully before dangerous buttons.
  • REFRESH SELECTED — re-fetch details for the selected service.
  • SET AS PREFERRED — remember this service id as the default for deploy/env actions.
  • DEPLOY LATEST — start a normal deploy of the latest code from the connected git repo.
  • CLEAR CACHE + DEPLOY LATEST — full rebuild (slower; use when a normal deploy still runs old weirdness).
  • SYNC LOCAL SECRETS → RENDER — push this console’s known secrets into the selected service’s Environment on Render.
  • ENV (MASKED) — show env var names (values hidden) for a sanity check.
  • PULL FULL ENV — pull actual values (sensitive — don’t share screenshots).
  • SUSPEND — pause the service (saves free-tier hours; bot goes down).
  • RESUME — wake a suspended service.

Logs

  • APP LOGS — what the running app is printing (errors, heartbeats).
  • BUILD LOGS — what happened while installing dependencies / building the image.
  • REQUEST LOGS — incoming HTTP requests (if available).
  • AUTO-REFRESH ON/OFF — keep reloading logs every few seconds while you watch a deploy.
Pick the right service before DEPLOY / SUSPEND / SYNC.
Bot and console are different. Deploying the wrong one won’t fix the other. Each service needs its own Environment keys.

9. LOCAL tab — run the bot on this computer

Only useful when the console is on your laptop/desktop and you want to start the bot as a process next door. On Render, leave this alone — the bot is already a separate Web Service.

  • START BOT — launch the bot process using local keys/config.
  • STOP BOT — stop that local process.
  • TAIL LOG — show recent local log lines.

10. DEPLOY tab — hosting cheat sheets

Click a target name (LOCAL, DOCKER, VPS, RENDER, RAILWAY, HEROKU, FLY.IO, VERCEL) to read a short guide for that style of hosting.

  • RENDER — what you’re probably using: create a Web Service, Python, connect the git repo, set Environment vars.
  • VERCEL is marked as a warning for a reason — it’s great for static frontends, not for a long-running Telegram bot process.
  • Static Site on Render = brochure pages only. It cannot run this Python console or the bot. Always choose Web Service.

Generate files from the ARTIFACTS tab before you try Docker / Fly / VPS recipes that expect those files.

11. ARTIFACTS tab — helper files for hosting

Creates ready-made config snippets (Docker compose, Render blueprint, systemd unit, etc.) into a folder on the machine. You usually only need this if you host outside the simple Render UI path.

  • GENERATE ALL — write/update the helper files.
  • LIST — show what files exist.
  • Click a file name in the list to preview it in the big text box.

12. How the bot answers (super short)

  1. Student asks a question in Telegram (optionally after picking a book).
  2. In a private chat you may see a live “Working…” draft bubble while it searches.
  3. The bot searches matching chunks in Pinecone (vector + keywords).
  4. Gemini writes a short, structured answer from those chunks.
  5. Faithfulness checks try to keep claims tied to the book text.
  6. The final card is a rich Telegram message (headings, lists, tables, expandable source notes) when your app supports Bot API 10.1+, with plain HTML as fallback.
  7. Student can page details, quiz, bookmark, make flashcards — study tools, not a doctor.

13. Common “why is it broken?” moments

  • Console says missing secrets but bot works in Telegram — Keys live only on the bot service. Copy Telegram + Gemini + Pinecone onto the console Environment too if you want LIBRARY uploads from the console.
  • STATUS says BOT OFFLINE but Telegram still replies — Free tier may be cold-starting; open the bot URL once, wait, refresh. Or BOT_BASE_URL is wrong / empty on the console. STATUS no longer depends only on a local process id.
  • Upload stuck near the start — Console needs Gemini + Pinecone. Big PDFs take minutes. Watch LIVE LOGS / heartbeats. Prefer uploading huge books from a PC if cloud request timeouts bite.
  • “Namespace not found” while clearing — First time that book name is used. Harmless.
  • Build failed mentioning pydantic / Python 3.14 — Use Python 3.11 on Render (runtime.txt in the repo pins this).
  • API key leaked in chat or git — Revoke it, create a new one, put it only in Environment / .env, never in code.
  • Two services, only one redeployed — Code or keys on the console don’t auto-appear on the bot. Deploy/env each service you care about.
  • Console asks for a password in the browser — You (or someone) set CONSOLE_PASSWORD. Default username is usually admin.

14. Safe habits

  • Always set CONSOLE_PASSWORD if the console is on the public internet.
  • Never paste real keys into Discord, Telegram groups, GitHub issues, or screenshots of SECRETS.
  • After rotating a key, update every service that needs it, then redeploy if the process already started with the old key.
  • Treat SUSPEND, CLEAR CACHE + DEPLOY, and SYNC SECRETS as “measure twice” buttons.
  • Notbook is a study library interface, not a doctor. Answers come from your uploaded books.

Tip: keep this DOCS tab open in a second browser window the first time you walk through STATUS → SECRETS → LINK → LIBRARY.
